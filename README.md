### ヒーローの写真（2026-08-12 追加）

トップのヒーローは球場の写真を **7秒ごとに** 切り替える（`HeroSlideshow`）。

| 場所 | 中身 |
|---|---|
| `assets/hero/` | 原本。リポジトリに入れる前の大きいまま |
| `public/hero/` | 配布用。**直接置き換えない**（`npm run hero` で作る） |
| `src/lib/hero.ts` | 表示する順番・クレジット・何が写っているかのメモ |

```
npm run hero
```

幅1920pxまで縮めて JPEG(q78) にする。スマホで撮った写真は2MBを超えることがあり、
リポジトリに履歴として残り続けるため、入れる前に一度だけ小さくする。

**写真の上には navy-900 の膜を重ねている**（`globals.css` の `.hero-veil`）。
写真ごとに明るさが違うので、素のまま白文字を載せるとコントラストが写真次第になる。
かといって一様に濃くすると写真が見えない。**見出しのある側だけ濃くしている。**

| 幅 | 膜 | 理由 |
|---|---|---|
| 1024px以上 | 左92% → 60%で86% → 82%で40% → 右端15% | 見出しが左だけなので右は写真を見せる |
| 1024px未満 | 一様に70% | 見出しが幅いっぱいに広がるので右だけ薄くできない |

濃さは「白文字が4.5:1を満たすか」で決めている。いちばん長い行はヒーローの幅の
**59%** で終わり、そこでの膜は86%。想定できるいちばん明るい背景（青空）の上でも
7.6:1 になる。**ヒーローの文言を長くしたら60%という区切りを見直すこと。**

被写体が左に寄っている写真は `flipHorizontal: true` で左右反転させ、
見出しと重ならないようにしている（`ball.jpg`）。
**文字が写っている写真には使わない**（鏡文字になる）。

**`prefers-reduced-motion: reduce` のときは切り替えない。** 自動で動き続ける背景は
設定で止められる必要がある（WCAG 2.2.2）。止めても1枚目が出るので情報は失われない。

写真は装飾なので `alt=""`。ただし**クレジットは読み上げ対象に残す**
（帰属表示は装飾ではなくライセンス上の義務）。

⚠️ **出典が確認できない写真を足さないこと。**
このサイトは広告を載せる＝営利なので、「個人利用のみ可」の素材は使えない。
`src/lib/hero.ts` の `source` に**必ず出典を書く**（画面には出さない記録用）。
`credit` のほうは画面に出すもので、表示義務があるときだけ入れる。

### 学校データの作り方

**学校名・所在地・設置区分は文部科学省「学校コード一覧」から機械的に取る。**
生成AIに学校名を書かせない（存在しない学校が必ず混ざる）。

```
node scripts/build-school-seed.mjs
```

CSVは初回だけ自動でダウンロードして `data/` に置く（gitには入れない）。
高校・中等教育学校は東日本／西日本の2本、**高専は大学・短大と同じ別ファイル**にある。
出力は `supabase/schools_<地方>.sql`。**このSQLは生成物なので直接編集しない。**

**必ず全地方を一度に作る**（引数なしで実行する）。slugの重複は地方をまたいで
起きるため（本庄と本荘、足立と安達、大野と小野はローマ字にすると同じになる）、
地方ごとに走らせると重複に気づけず、INSERT時に後の学校が前の学校を上書きしてしまう。
重複したときは後から来たほうに地区名を足して分ける（`saitama-honjo` など）。
**先に処理した地方が短いslugを取るので、地方を足すときは `REGIONS` の末尾に足すこと。**
途中に入れると既存のURLが変わる。

公的データに無くて補っているのは3つだけ。

| ファイル | 補うもの | なぜ必要か |
|---|---|---|
| `data/school-kana.json` | 校名の読み | CSVにふりがなが無く、URLのローマ字slugが作れない |
| `data/name-override.json` | 表示名 | 分校や「川口市立高等学校」など、機械的に短縮できない校名 |
| `data/establishment-override.json` | 設置区分 | 校名に設置者が入っていない学校（ふたば未来学園など） |
| `data/district-override.json` | 地区 | 住所から決められない学校があれば学校コードで指定する |
| `data/hokkaido-shinkokyoku.json` | 振興局 | 北海道の南北を市町村から決めるための対応表 |
| `data/baseball-clubs.json` | 硬式野球部の有無 | 文科省データに部活動が無い。各県高野連の加盟校名簿から |

### 硬式野球部の絞り込み

掲載するのは硬式野球部がある学校だけにする。判断は**各都道府県高野連の加盟校名簿**に
よる。**推測で決めない**（校名や設置区分からは分からない）。

`data/baseball-clubs.json` に名簿を県ごとに入れる。名簿がある県は、載っていない学校を
`status = 'draft'` にする（RLSで公開側から見えなくなる）。**消さずに下書きにする**のは、
名簿が変わったときに戻せるようにするため。名簿を入れていない県は全校を公開したままに
する。全部を下書きにするとサイトから学校が消えてしまうので、調べた県から順に絞る。

名簿は「千葉」「市立千葉」「東金商」「木更津高専」のような短縮形で書かれている。
照合は 芯 →「市立」付き → 高専の言い換え → 省略形の補完（商→商業など、残りが
1文字のときだけ）の順で行い、**照合できなかったものは両方向とも報告する**。
実行結果の「名簿にあって照合できず」が0件になるまで確かめること。

名簿を入れていない県でも、**校名に「女子」が入る学校は下書きにする。**
高野連の硬式は男子のみで女子校は加盟できないため、校名から機械的に判断できる
数少ない確実な除外条件。ただし奈良女子大学附属中等教育学校のように
名前に女子が入っていても共学の学校があるので、`CO_ED_DESPITE_NAME` で除く。

読みは芯の部分（「千葉県立千葉高等学校」なら「千葉」）をキーにする。
同じ芯で読みが違う学校（麻生＝あそう／あさお、東＝あずま／ひがし）は
**学校コードをキーにして個別に指定する。**
値をローマ字で書くと変換せずそのままslugになる（広尾＝hiroo など、
長音ではない母音の並びで使う）。

**読みは目視で確認すること。** slugは公開後に変えられない。

地区の判定は住所から機械的に行っている。東京は多摩地域＋世田谷・練馬・杉並が
西東京、北海道は振興局（石狩・空知・後志・胆振・日高・渡島・檜山が南）。
区割りが変わったらスクリプト内の `resolveTokyoDistrict` と
`data/hokkaido-shinkokyoku.json` を直す。

#### 成績（`result`）の決め方

**「3勝」ではなく「ベスト16」のように到達段階で持つ。**
勝ち抜き戦なので、試合の勝敗グラフを決勝までさかのぼれば、
その試合が決勝の何回戦前か（k）が確定する。k=0の敗者が準優勝、k=1が4強、
k=2が8強……と2倍ずつ増える。**決勝から逆算するのでシードや不戦勝の影響を受けない。**

実装で踏んだ落とし穴が2つある。直すときは注意すること。

- **勝者の残り試合数を数えてはいけない。** 勝者は次に負ければそこで終わるので、
  それだと決勝以外のほぼ全試合が「決勝の1つ前」になり、ベスト4が1大会あたり
  4.6校という結果になる。**「勝者が次に出る試合」を辿って決勝まで遡る**のが正しい
- **無敗であることを優勝の根拠にしてはいけない。** 負け試合を取りこぼした学校も
  敗戦0になるため、偽の優勝校ができる。**優勝は決勝の勝者に限る**

到達段階が確定しない場合（試合を取りこぼしている、敗戦が2つある、開催中）は
**推測で埋めず `result` を null にする。** 現在110件（1.7%）。

分布は次のとおりで、大会数199に対して整合している。

| 優勝 | 準優勝 | ベスト4 | ベスト8 | ベスト16 | ベスト32 | 初戦敗退 | 不明 |
|---|---|---|---|---|---|---|---|
| 195 | 191 | 391 | 762 | 1,103 | 443 | 3,142 | 110 |

**照合キーは表示名ではなく記事名にしている。**「銚子商」ではなく
`[[千葉県立銚子商業高等学校|銚子商]]` のリンク先を使う。さらに好都合なことに、
統廃合・改称した学校はWikipedia側が既に現存校の記事を指している

一致するので、旧校名の対応表はほぼ不要になった。**

**中止大会を取り込まない。** 1918年（夏第4回・米騒動）、1941年（夏第27回）、

   出てくる場合。片方向だけだと「近隣校へのリンク」を後身校と誤認するため、
   **両方の記事が関係を裏付けているときだけ**採用する

## 記録・ランキング（2026-08-12 実装）

`/rankings` 以下。**DBの変更は無い。** 既存の `school_championships` を集計し、
足りないぶんだけリポジトリ内の生成データで補っている。マイグレーションを
適用しなくてもそのまま動く。

| URL | 内容 |
|---|---|
| `/rankings` | ハブ。主要な数字とトップ10、各ページへの入口 |
| `/rankings/koshien` | 出場回数（春／夏／通算）・通算勝利数・勝率。`?season=` `?metric=` |
| `/rankings/best` | 到達段階ごとの学校一覧（優勝→初戦敗退）。`?season=` |
| `/rankings/21seiki-waku` | 21世紀枠の年表と都道府県別の選出回数 |
| `/rankings/prefectures` | 都道府県別の出場回数・勝利数・出場校数（タイル地図の色分け）。`?metric=` |
| `/rankings/history` | 出場校に公立が占める割合の100年の推移 |

### 集計をDBのビューにしなかった理由

ビューを足すと**人がSQL Editorで適用する作業が増え、忘れるとページが落ちる。**
対象は出場歴2,987件・学校687校で、1回あたり4リクエスト・1.5秒。
ページの `revalidate` は1日（出場歴が増えるのは年2回）。これで足りている。

重くなったら 0007 でビューを足して `src/lib/queries/rankings.ts` の中身だけ
差し替える。戻り値の形を保てば画面側は変えなくてよい。

**PostgREST は1回に1,000行しか返さない**ので、出場歴はページングで取っている。
`.range()` を使うときは**並び順を一意に決めてから**にすること
（`school_id, year, season`）。並びが不定だとページの境目で行が重複したり抜けたりする。

### リポジトリ内の生成データ

| ファイル | 作るもの | 中身 |
|---|---|---|
| `src/lib/data/twenty-first-century.ts` | `build-21st-century.mjs` | 21世紀枠 70件（2001〜2026） |
| `src/lib/data/koshien-tournaments.ts` | `build-koshien-summary.mjs` | 大会199件の出場校数・試合数 |

**どちらも生成物。直接編集しない。**

**毎年やること**（選抜の選考が終わる1月末〜2月、選手権が終わる8月末）

```
node scripts/fetch-koshien-wikipedia.mjs        # 新しい大会の記事を取る
node scripts/build-koshien-seed.mjs             # 解析
node scripts/match-koshien.mjs --write          # supabase/koshien.sql を作り直す → SQL Editor で流す
node scripts/build-koshien-summary.mjs          # 分母（大会ごとの出場校数）を更新
node scripts/build-21st-century.mjs --refresh   # 21世紀枠を更新
```

`koshien.sql` は `on conflict do update` なので、何度流しても安全。
流したあとに `select public.recalc_school_koshien_counts();` を忘れないこと。

- 21世紀枠は年に1〜3件しか増えないので、テーブルを1つ増やして適用の手間を
  かけるより生成物のほうが軽い。毎年1月の選考後に `--refresh` で作り直す
- 大会ごとの出場校数は「公立が何割か」の**分母**に使う。私立を含む数なので
  DBには無い（このサイトは公立しか収録しない）

### 21世紀枠の取り込み

出典は Wikipedia「選抜高等学校野球大会」の「21世紀枠出場校一覧」。
**大会別記事ではなく親記事を使っている**。独立した「21世紀枠」節を持つのは
26大会中11大会だけで、残りは選出校の表に紛れているため。親記事の一覧は
2001年から現在まで1つの表にまとまっていて書式も一貫している。

取り込むのは**年・地区区分・校名だけ**。

- **選考理由の文章は取り込まない。** 記事の文章を持ってくるとCC BY-SAの
  継承条件が発動する（事実データの抽出では発動しない）
- **成績もこの表からは取らない。** この表は「2回戦敗退」、DBは「ベスト16」と
  表記が違う。同じ出場が2つの表記を持つのを避け、DB側に一本化している

**統廃合前の校名は同じ年の出場校表から引き当てている。** 親記事の表は
「北海道女満別高等学校」のまま残っているが、大会別記事のほうは現存校
（北海道大空高等学校）に張り替えられている。21世紀枠の学校は必ずその年の
選抜に出場しているので、**同じ出典の中で現存校の記事名が手に入る**。
校名を推測で書き換えてはいない。

照合結果は70件中69件。残る1件は土佐（高知）で、これは私立なので
学校マスタに無くて正しい（Wikipedia自身も21世紀枠で選ばれた私立は
この1校だけと書いている）。

自己検証を2つ入れてある。どちらも現在0件。

| 検証 | 内容 |
|---|---|
| 1 | 照合できた学校が、その年の選抜の出場校の中にいるか（中止年を除く） |
| 2 | 表に書かれた都道府県と、照合先の学校の正式名称が食い違わないか |

### 表示で気をつけていること

- **「私立を収録していない」と各ページに必ず書く**（`DataNote` コンポーネント）。
  学校マスタが公立だけなので、ここでの1位は全国1位ではない
- **成績が不明な出場を「初戦敗退」に混ぜない。** 最高成績の一覧では、
  段階が確定しない学校はどの段階にも入れず、注記で数だけ出す
- **春・夏の切り替えはリンクで作る**（クライアントJSを使わない）。
  状態がURLに残るので共有でき、検索エンジンにも拾われる
- **地図の色はネイビーの濃淡だけ。** 明度だけで並べれば、色覚特性があっても
  白黒印刷でも段階の順序が保たれる。折れ線は色と線種の両方で見分ける
- **値の種類が段階数以下のときは分位で切らない。** 21世紀枠の選出回数のように
  1〜4しか値が無いデータを分位で切ると「1〜／1〜／1〜」という凡例になる

## 公立旋風の勝ち上がり（2026-08-12 実装）

公立旋風の詳細ページ（`/phenomenon/[slug]`）に、甲子園での勝ち上がりを
1試合ずつ出す。1回戦から決勝まで、回戦・対戦相手・スコア・寸評を縦に並べる。

| ファイル | 役割 |
|---|---|

| `src/components/phenomenon/TournamentRun.tsx` | 表示 |

### なぜDBに入れないのか

試合単位のテーブルを足すと、人がSQL Editorで流す作業が1つ増え、
流し忘れると詳細ページが落ちる。記事は数十件の規模で、更新も編集作業の
一部なので、コードと一緒にデプロイされるほうが事故が少ない。
記録・ランキングでビューを作らなかったのと同じ判断。

**`src/lib/content/` は手で書く編集コンテンツ。`src/lib/data/` は
スクリプトの生成物（直接編集しない）。** 紛らわしいので置き場所を分けてある。

`phenomena.slug` と `TournamentRun.phenomenonSlug` が対応している。
片方を変えるならもう片方も変えること（勝ち上がりが出なくなるだけで
ページは落ちないので、気づきにくい）。

### 出典の集め方

大会記事のブラケットには**最終スコアしか無い**。イニングごとの得点は
別のところから取る必要がある。

1. **旋風そのものの独立記事を先に探す。** 「金農旋風」には全6試合の
   Linescoreと試合経過がある。「大社旋風」は記事が無く、「がばい旋風」は
   大会記事へのリダイレクト。
2. **試合単体の記事を探す。** 「宇治山田商業対佐賀北延長15回引き分け再試合」
   のように、有名な試合には個別記事があってLinescoreを2つ持っている。
3. **無ければ運営者のスコアブック。** 当時つけた一次記録があるならそれが最良。

`scripts/fetch-wikipedia-pages.mjs` で記事名を指定して wikitext を取れる。

```
node scripts/fetch-wikipedia-pages.mjs "金農旋風" "秋田県立金足農業高等学校"
```

#### ★新聞社のスコアページは使わない

**一球速報.com とバーチャル高校野球は使えない。** 外した理由は著作権ではなく
**利用規約**で、上の「出典の選定」に条項まで控えてある。特に
バーチャル高校野球は第8項(3)で**営利目的の利用を禁じており、
目視での転記も塞がる**。「人が読んで数字を渡せば規約に触れない」は
**この2媒体には通用しない**（2026-08-12 にこの誤りをやりかけた）。

他の新聞社も「無断転載禁止」「営利利用禁止」を置いていることが多く、
**媒体を変える方向では解けにくい**。規約の壁を構造的に抜けるのは次の3つ。

| 手段 | 可否 | 備考 |
|---|---|---|
| 運営者自身のスコアブック | ◎ | 一次記録。規約に縛られない。**いま13試合ぶんある** |
| 市販の記録集（書籍） | ◎ | 書籍に利用規約は無い。事実の転記は自由 |
| 日本高野連の公式ページ | △ | 規約なし・一次情報だが**当年分しか残らない** |

**戦評の文章はどの出典でも写さない。** 事実だけを取って自分の言葉で書く。

⚠️ **出典の表示は実際の出所と一致させること。** 手元に同じ記録があっても、
私が転記した経路が別なら、その経路が本当の出所。読者に対する出典表示の
信頼性は、規約の問題より優先する。

## 結果速報の自動更新（2026-08-12 実装）

|---|---|

```
node --env-file=.env.local scripts/build-live-results.mjs --dry   # 報告だけ
node --env-file=.env.local scripts/build-live-results.mjs         # 生成する
```

### なぜDBに書かないのか

**`service_role` キーを持たない設計を崩さないため。** DBに書くには
RLSを全部バイパスするキーが要り、CIに置くとリスクが増える。生成物を
リポジトリに置けば anon キーだけで済み、**差分がGitに残るので
Wikipediaが荒らされても後から追える。**

出場歴（`school_championships`）は大会終了後に1回だけSQLで入れる。
**日常運用は完全自動、人が動くのは年2回。**

## SEO（2026-08-12 に大きな修正が2つ）

### 1. sitemap から2,505校が抜けていた（修正済み）

`getAllSchoolSlugs()` がページングしておらず、**PostgREST の1,000行制限で
3,505校のうち1,000校しか返っていなかった。** sitemap も
`generateStaticParams` もこれを使っているので、公開していたら
2,505校が sitemap から丸ごと抜けたまま気づかなかった可能性が高い。

**このリポジトリで3度目の同じ罠。**（出場歴の集計・ランキング・今回）
`select()` で全件取るコードを書いたら、**必ず一意な並び順を決めてページングする。**

### 2. 約2,827校が「薄いコンテンツ」だった（noindex にした）

甲子園出場歴があるのは**678校だけ**。残り約2,827校のページは校名・所在地・
区分しか無く、あとは「まだありません」が3つ並ぶだけになる。
同じ形の空ページが2,800枚あると、サイト全体が薄いと判定され、
**ランキングや公立旋風など中身のあるページの評価まで巻き添えになる。**

対処は次の2点。中身が入れば**自動で両方に復帰する**ので手作業は要らない。

| 場所 | やっていること |
|---|---|
| `app/schools/[slug]/page.tsx` の `isIndexable()` | 出場歴が無ければ `noindex, follow` |
| `getIndexableSchoolSlugs()` | sitemap には出場歴のある学校だけ載せる |

**`follow` は残している。** 閲覧も内部リンクの評価も従来どおり。

⚠️ **戦績（`school_records`）やニュースを入れ始めたら `isIndexable()` に
それも足すこと。** いまは実データが0件なので出場歴だけで判定している。

### SEOで狙うべきところ

**結果速報で検索流入は取れない。** 「◯◯高校 結果」で朝日・毎日・スポーツ紙に
速度でも権威でも勝てない。結果速報の価値は回遊と再訪であって検索ではない。

検索で取れるのはストック側。

| 狙える | 例 |
|---|---|
| 学校の記録 | 「熊本工業 甲子園 出場回数」 |
| ランキング | 「公立 甲子園 優勝」「21世紀枠 一覧」 |
| 公立旋風 | 「金農旋風」「大社 2024」 |

### なぜ学校ページに自由記述欄を置かないか

置くと「○○高校の△△君」という書き込みが出る。このサイトは
**選手個人のページ・個人成績は作らない**（未成年への配慮）と決めているので、
自分が載せないと決めた情報を利用者に書かせる場所も作らない。
文字で応援したい人は都道府県ページのメッセージ欄へ導線を張ってある。

### 守りの構造

**anonキーは公開鍵なので、アプリを経由しない書き込みが常に可能。**
Next.js の API ルートを挟んでも裏口は塞げないため、検査はすべてDB側にある。

| 層 | 何をしているか |
|---|---|
| RLSポリシー | 投稿できる行の形を縛る（`status = 'draft'` のみ等） |
| トリガ | `status`・公開日時をサーバ側で強制上書き。ポリシーは列追加時の追従漏れがあるため二重化 |
| CHECK制約 | 本文200字・表示名20字・`visitor_key` の形（16〜64字の英数字とハイフン） |
| レート制限 | 同一 `visitor_key` から1時間5件まで |
| 権限 | anon から `update` / `delete` を revoke |

`school_cheers` と `poll_votes` は **書けるが読めない**（select ポリシーを作っていない）。
誰がどこを応援したかを返す必要が無く、返せば利用者の行動履歴を配ることになるため。
表示に使う数は `schools.cheer_count` と `poll_options.vote_count` にある。

**visitor_key は本人確認ではない。** ブラウザの localStorage に置くUUIDで、
消せば別人になれる。二重クリックとカジュアルな連投を防ぐためのもの。
本格的な荒らし対策が要るようになったら Supabase Auth を入れ、`user.id` に置き換える。

### 運用でやること

- **投稿の承認。** `cheer_messages` は必ず `draft` で入る。ダッシュボードの
  Table Editor で `status` を `published` にすると公開される（`published_at` は自動）
- **管理画面はまだ無い。** 件数が増えたら作る
- **公開前に必要なもの** — 利用者の投稿を預かる以上、運営者情報の設定・
  利用規約・削除方針・通報導線は公開までに揃える（下記「公開前に必ずやること」）

```
node --env-file=.env.local scripts/check-community.mjs
```

RLSとトリガが効いているかを anon キーで13項目確認する。**本番DBに書き込む**ので、
実行後は出力される掃除用SQLでテスト行を消すこと。

### MVPに含めていないもの

ユーザー登録・ログイン・学校フォロー・投稿・コメント・通知 /
ニュース自動収集 / 管理画面 / X自動投稿 / 広告の実配信 / アフィリエイト

いずれも将来追加しやすい形にはしてある（`AdSlot` の空実装、RLSの先行有効化など）。

## 設計上の決めごと

`AGENTS.md` に集約してある。**コードを触る前に必ず読むこと。**
特に重要なのは以下。

- 収録対象は「私立以外」。**国立・高専も含む**
- 東京都立**国立**高校（くにたち）は「都立」。設置区分を機械判定しない
- ニュースは全文転載しない。見出し＋自作要約＋出典リンクまで
- 選手個人のページ・個人成績は作らない
- 未公開コンテンツの除外は**RLSで強制**。クエリに `status='published'` を書かない
- `src/types/database.ts` は手書き。マイグレーションを変えたら必ず合わせる
- オレンジは白地では4.5:1を取れない。白地の文字には `accent-800` を使う
